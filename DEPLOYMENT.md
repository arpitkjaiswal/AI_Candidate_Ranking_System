# Deploy the ranking application

React, the FastAPI API, and SQLite run together as one Docker web service. No separate frontend host or hosted database is required for a private, single-instance installation. User data must live on persistent storage at `/var/data`.

## Recommended first deployment: Render

1. Commit and push the updated application, `Dockerfile`, `render.yaml`, lockfiles, and this guide to your GitHub repository. These local changes must reach the branch Render deploys.
2. In Render, choose **New → Blueprint**, connect `arpitkjaiswal/AI_Candidate_Ranking_System`, select that branch, and let Render read `render.yaml`.
3. Review the proposed paid web service and persistent disk before creating resources. The included Starter plan is for a small demo. The full 100K-candidate dataset needs memory and disk sizing based on load testing; it is not validated on Starter.
4. Deploy the Blueprint. Docker builds the React assets and Python API. The container prepares mounted-storage ownership, then starts the server as the unprivileged `app` user. `/health` is the readiness probe.
5. In the service's Environment settings, retrieve the generated `APP_PASSWORD` securely. Open the HTTPS address Render provides and sign in through the browser prompt: username **admin**, password **the generated APP_PASSWORD**. Do not copy the password into GitHub or frontend variables.
6. Open **Candidates**, import a JSONL file, then create a job with its description. Open **Pipeline**, select the job, run ranking, and follow **View completed rankings**. Uploads are limited to 50 MiB; imports add/update candidates and reject invalid data atomically.
7. Restart the Render service and confirm candidate profiles, jobs and completed rankings remain. Code deployments retain the disk; live background runs are interrupted and marked failed so they can be retried.

The disk is included in `render.yaml` at `/var/data`. Do not remove it or switch to ephemeral storage. The Blueprint generates the authentication password; never clear it on a public service.

### Environment settings

| Setting | Value / purpose |
| --- | --- |
| `DATA_DIR` | `/var/data`; SQLite database, uploads and per-run artifacts |
| `APP_USERNAME` | `admin`, or choose another login name |
| `APP_PASSWORD` | Generated by the Blueprint; keep it secret |
| `DEMO_MODE` | `true` seeds two fictional profiles only when the database is empty; use `false` for an initially empty real installation |
| `CANDIDATES_PATH` | Optional existing JSONL/JSONL.GZ file inside `/var/data`; leave unset for browser uploads |
| `CANDIDATES_URL` | Optional HTTPS dataset download for an empty database; enter signed URLs as hosting secrets |
| `PORT` | Supplied by Render; do not hard-code another port |

Browser import works on an existing database: do not delete or move it to add real candidates. A normal pipeline run uses all current database candidates. Choosing the link after an upload ranks only that uploaded dataset. Uploading changed profiles invalidates their earlier scores; rerun affected jobs to refresh rankings.

For a dataset larger than the browser limit, upload it securely to your persistent storage and point `CANDIDATES_PATH` at it, or configure `CANDIDATES_URL` before first startup. Existing databases are preserved and are not automatically replaced by a new URL. Do not commit candidate data or signed URLs.

## Docker on your own machine or server

Install Docker Engine with Compose, then from the repository:

```sh
# Set APP_PASSWORD securely in your shell or an ignored local .env file first.
docker compose up --build -d
docker compose logs --tail=100 app
docker compose ps
```

Compose binds port 8000 to `127.0.0.1` by default, and the named `ranking-data` volume retains SQLite across restarts. Place a TLS reverse proxy in front of the service for remote access. Use `HOST_IP` and `PORT` only when you intend to change the host binding; configure `APP_PASSWORD` before exposing it publicly. Never use Basic authentication over unencrypted remote HTTP.

Restart without deleting data:

```sh
docker compose restart app
```

Do not run `docker compose down -v` unless you intend to permanently delete the named database volume.

## Backups, resources, and recovery

Create a consistent SQLite backup while the app is running:

```sh
docker compose exec app python -m backend.manage backup /var/data/backups/ranking-2026-11-03.sqlite
```

Choose a new destination each time; the command refuses to overwrite existing backups. On Render, run the equivalent Python command through the service shell. Copy backups to separate protected storage; a backup on the same disk does not protect against disk deletion. Test restoration on a separate instance before using a backup for recovery. Stop the service before replacing its database, and preserve its current database and WAL files first.

Keep **one instance and one Uvicorn worker**. SQLite admission checks allow one ranking run at a time. A multi-instance service needs a shared database and durable worker queue; that architecture is not implemented here.

The pipeline currently loads profile data and features into memory. Do not assume a large JSONL file fits into the smallest hosting plan. Each successful run retains its model artifacts and canonical input under `DATA_DIR/runs/<run_id>`. Monitor free disk space and archive or remove only finished-run artifacts after backups and storage review. Preserve `redrob_candidates.db` and any source uploads still in use. Removing run artifacts does not delete database ranking rows, but removes the files needed to reproduce that exact run.

## Validate a deployment

- `/health` responds successfully without credentials so the host can probe readiness.
- The homepage and `/api/candidates` require authentication when `APP_PASSWORD` is set.
- Import two sample candidates, create a job, run it to **done**, and inspect both rankings and profile features.
- Restart the service; verify candidate counts and completed rankings persist.
- Attempt an invalid JSONL import; it should report an error and leave the database unchanged.

For automated checks, run the backend suite with development dependencies and the Chromium suite against an isolated test service:

```sh
venv/bin/pip install -r requirements-dev.txt
venv/bin/python -m pytest -q
# Start an isolated app first. Provide TEST_BASE_URL and, if protected,
# TEST_USERNAME / TEST_PASSWORD through your secure process environment.
npm run test:e2e --prefix frontend
```

A complete image-level check is available too:

```sh
docker build -t redrob-ranking:release .
python3 scripts/verify_container.py
```

It creates and removes its own test container and volume, checks mounted-disk permissions and the unprivileged server user, verifies authentication, ranking, SQLite backups and restart persistence, then runs the authenticated browser suite. It needs the local Docker socket and free loopback port 8020. The CI container job runs this check as well.

The browser suite creates test profiles and jobs. Do not point it at real candidate data. The challenge CLI uses a different SQLite schema; keep its output separate from the API's `DATA_DIR`, for example `precomputed/cli`.

The ranking model measures profile/job matches; scores are not calibrated hiring probabilities. Local functional validation does not establish real-world hiring quality, full-dataset performance, or a production SLA. Deployment instructions are prepared; no hosting account has been used to publish this application from this workspace.
